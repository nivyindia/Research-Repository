# Source Audit and Migration Plan

## 1. Sources to inspect
1. Google Drive — Partner Welcome Kit folder.
2. Google Drive — Distributor Field Kit folder.
3. Google Drive — Training Folder.
4. Any approved service catalogue, pricing/commission sheet, distributor/franchise agreement, onboarding/KYC checklist, SOP, support policy, marketing policy and brand assets referenced by those folders.
5. Relevant existing files already present in this GitHub kit structure.

The Google Drive file-level audit is **pending**. This document describes the method; it is not evidence that the audit has happened.

## 2. Inventory fields
For every source file, capture:
- Unique audit ID.
- Exact source folder and original path/link.
- Original file name and file type.
- Modified/created date or version if available.
- Owner/author/approver if known.
- Primary audience: Retailer/Franchisee, Distributor, both, internal-only.
- Subject/topic and target outline-register row.
- Status: approved, draft, outdated, unknown, duplicate, conflicting, restricted or irrelevant.
- Key facts extracted and exact source location/page/section.
- Destination path (proposed and final).
- Migration status and date.
- Conflict/missing information and follow-up owner/action.

## 3. Audit workflow
1. List every file in each source folder, including subfolders.
2. Inspect relevant files rather than relying on names alone.
3. Preserve source names, paths and version metadata.
4. Map each file to one or more rows in the File Outline Register.
5. Identify duplicates and versions; compare before selecting a canonical copy.
6. Flag conflicting service names, prices, commissions, incentives, payment cycles, document requirements, support promises and company facts.
7. Distinguish source statements from assumptions and from current policy.
8. Propose a destination for each useful file.
9. Do not delete or overwrite original source material during migration.
10. Record excluded material and reason; archive superseded GitHub copies with links where appropriate.
11. Update the Progress Tracker and Decisions and Open Questions after each audit batch.

## 4. Coverage labels
- **Existing — verified:** source clearly covers requirement and is current/approved.
- **Partial:** some required detail is present, but gaps remain.
- **Missing:** no supporting source found.
- **Conflict:** multiple sources disagree.
- **Outdated:** exists but appears superseded or past its effective date.
- **Needs confirmation:** status/authority/currentness unclear.
- **Not applicable:** requirement does not apply, with reason recorded.

## 5. Priority
- **P0 — release blocker:** commercial terms, pricing, commissions, statutory/third-party charges, settlement, lead/marketing promises, legal/compliance terms, service availability.
- **P1 — operational critical:** onboarding, required documents, fulfilment SOP, payment workflow, complaint/escalation, customer communication.
- **P2 — enablement:** training, scripts, collateral, CRM, reporting, competitor research.
- **P3 — polish:** layout, styling, nonessential supplementary examples.

## 6. Migration safety
- Keep a source-to-destination map.
- Do not treat a file copy as approved content.
- Do not place completed KYC/customer data, identity scans, passwords or sensitive personal data in GitHub.
- Redact personal/customer information before extracting reusable templates.
- Preserve historical copies where a policy or commercial version changed.
- Mark unverified documents clearly; never silently merge contradictory terms.
- Obtain authorized confirmation for a canonical commercial source.

## 7. Audit outputs
- Source Inventory Register.
- Outline-to-Source Coverage Matrix.
- Duplicate and Conflict Register.
- Missing Information / Decision List.
- Migration Log.
- Updated Progress Tracker.
